1.2
Scope
The Qi Specification, MPP Communications Protocol (this document) defines the messaging between a Power Transmitter
and a Power Receiver specific to the Magnetic Protocol used for the MPP Power Profile. The primary purpose of this
messaging is to set up and control the power transfer. As a secondary purpose, it provides a transport mechanism for
higher level applications such as Authentication. The communications protocol comprises both the required order and
timing relations of successive messages.

1.5.4
Notation of text strings
Text strings consist of a sequence of printable ASCII characters (i.e. in the range of 0x20 to 0x7E) enclosed in double
quotes ("). Text strings are stored in fields of data structures with the first character of the string at the lowest byte
offset, and are padded with ASCII NUL (0x00) characters to the end of the field where necessary.
EXAMPLE:
The text string “WPC” is stored in a six-byte fields as the sequence of characters 'W', 'P', 'C', NUL, NUL, and
NUL. The text string “M:4D3A” is stored in a six-byte field as the sequence 'M', ':', '4', 'D', '3', and 'A'.
1.5.5
Short-hand notation for data packets
In many instances, the Qi Specification refers to a data packet using the following shorthand notation:
<MNEMONIC>/<modifier>
In this notation, <MNEMONIC> refers to the data packet's mnemonic defined in the Qi Specification, Communications
Protocol, and <modifier> refers to a particular value in a field of the data packet. The definitions of the data packets in
the Qi Specification,Communications Protocol, list the meanings of the modifiers.
For example, EPT/cc refers to an End Power Transfer data packet having its End Power Transfer code field set to 0x01.

l Baseline Protocol: A power transfer protocol that which uses Power Receiver-to-Power Transmitter
communications only.
l The Communications Physical Layer book defines the low-level formats of data bits, data bytes, and data
packets.
l The Communications Protocol book defines the payloads of the data packets and their use in the power
transfer protocols.
l Extended Protocol: A power transfer protocol that supports bi-directional communications and enhanced Foreign
Object Detection (FOD) features, as well as data transport stream functionality and authentication options.
l Magnetic Protocol: A power transfer protocol that relies on the presence of magnetic attachment or active
alignment functionality for more efficient power transfer. It supports two operating modes:
l Restricted Mode: One-way communications (PRx to PTx) with limited power levels.
l Full Mode: Bi-directional communications enabling negotiation of higher power levels and improved FOD.
l Authentication: A tamper-resistant protocol by which a power receiver can verify the identity of a Power
Transmitter.
l Termination magnets: Magnets within a magnetic cover that block the propagation of the magnetic attachment
field to the PRx.
l Feedthrough magnets: Magnets within a magnetic cover that circulate the magnetic attachment field through the
PRx.
l Power Modes: Power delivery optimisations designed to maximise efficiency and performance within specific
power ranges.
l Gain Linearization: A control error calculation method that speeds up convergence of the power level control.
l Open air Q FOD: A pre-power foreign object detection method used to detect the presence of foreign objects
placed on the PTx prior to mating the PRx.
l Mated Q FOD: A pre-power foreign object detection method used to detect the presence of foreign objects when
the PTx and PRx are mated.
l MPLA FOD: A method to detect the presence of foreign objects that uses power loss accounting during the power
transfer.
l MPLA2 FOD: An enhanced version of MPLA FOD.
l FOD Delta Ploss calibration: A method to detect the presence of foreign objects that uses a calibrated power loss
during the power transfer.
l Thermal Management: A method of controlling the temperature of PTx and PRx products.

2.
Introduction
2.1
Overview
Magnetic power profile (MPP) is a protocol extension that provides additional messages, new power states/modes, new
power transfer contract elements, and aims to provide the following functionalities:
l Operating Frequency Negotiation
l Cloaking (Power Pause)
l Generic Information Exchange
l Simultaneous Data Stream Transactions
l Fast PTx to PRx communication
l Maximum Power and Power Control Profiles Determination
l Extended Power Negotiation
l Extended PTx/PRx Identification and Capabilities
l Extended Control Error Packets and Received Power Packets
l Power Transmitter Battery Level Reporting
l Ecosystem Scalability
A summary of differences between Magnetic Power Profile and EPP is listed below in Table 8.
MPP extension allows devices to operate under Restricted mode (no PTx communication) at 360 kHz without
performing any explicit negotiation with the Power Transmitter. This flexibility enables devices with limited resources

3.
Magnetic Power Profile    
3.1
Overview
This chapter describes the Power Receiver and Power Transmitter requirements for Magnetic Power Profile and the
modes devices may use to communicate.
MPP supports three protocol modes:
1. Restricted Mode: One-way communication (PRx to PTx) with limited power levels (5 W PRECT) using Qi
Baseline Protocol
2. 15 W Full Mode: Supports bi-directional communication and enables negotiation of power levels up to 15 W
3. 25 W Full Mode: Supports bi-directional communication and enables negotiation of power levels up to 25 W,
and power mode optimizations
3.1.1
Restricted Mode
MPP Restricted mode allows PRx to establish a charging session with PTx using one-way communication (PRx to PTx) at
360 kHz operating frequency using Qi Baseline Protocol.
When operating in the Restricted Mode of the Magnetic Protocol, the Power Transmitter and Power Receiver shall use
the Baseline Protocol with the following extensions:
l The Power Transmitter shall send an MPP Response Pattern in the Power Control Hold-off time interval after
each CE data packet.
l The Power Receiver may send a NEGO data packet after receiving an MPP Response Pattern to transition to the
Full Mode of the Magnetic Protocol.
See Section 5.7.2, Transition without power interruption , for details about the timings involved with these extensions.
NOTE: (Informative) MPP Restricted mode can be used when PRx is operating under a constrained environment e.g., device is fully
discharged
PRx is allowed to transition from MPP Restricted to MPP Full Mode to enable bi-directional communication and higher
power levels. Refer to Section 5.7, MPP-Restricted to Full Mode Transition for more details on how to perform the
transition.
3.1.2
15 W Full Mode
MPP Full Mode enables a charging session with bi-directional communication between PTx and PRx allowing devices to
perform more complex operations such as exchange of identification information, devices capabilities, ecosystem
scalability coefficients, power negotiation and perform authentication.
In MPP Full Mode, devices may transition between different protocol phases such as Negotiation, Power Transfer, Cloak
and are able to negotiate higher power levels compared to Restricted mode.
MPP Full Mode is based on Qi Extended Power Profile (EPP) protocol. PTx and PRx shall follow the Qi EPP specifications
when operating in this mode. Changes to the EPP specifications are explicitly stated in this document.
Changes to specifications include:

3.3.3
Startup Behavior
After detecting PRx placement on the charging surface, MPP PTx shall perform digital ping and identify the Power
Receiver using the information embedded in ID and XID packets as described in Section 3.2.2, Startup Behavior .
From the Power Transmitter's ’s perspective, a PRx supports MPP if both of the following conditions are satisfied:
1. Qi Version: Qi protocol version in ID packet (Section 3.2.2, Startup Behavior ) is set to (Major=2, Minor=0) or
higher.
2. MPP Support Advertised: Sub-header (byte 0) in XID packet is set to MPP selector (Section 8.1.29, Qi MPP
Extended Identification - MPP-XID (0x81) )
If the conditions are not satisfied, the Power Transmitter shall proceed to the next phase according to the Qi
specifications.
Depending on the digital ping level used to establish the communication at 128 kHz frequency, PTx shall set an internal
error status as following:
l Error = None: Communication at 128 kHz was established using ’Qi_HB_Low’ digital ping level
l Error = digital ping level mismatch: Otherwise
PTx shall then proceed to the requested MPP operation mode reported in MPP-XID packet as following:
l Activate Restricted Mode: If Restricted flag is set to one.
l Activate Full mode: If Restricted flag is set to zero.
PTx shall clear the error status if it decides to remove the power signal for any reason i.e., error status shall not persist
across communication restarts.
MPP Restricted Mode
PRx may choose to operate under MPP- Restricted Power Mode by setting the Restricted field in MPP-XID packet to 1.
PTx shall decode the MPP-XID packet and proceed as following:
l If active frequency is 360 kHz: Proceed assuming MPP Restricted mode
l Else: Proceed depending on the error status
If the error status is not set, PTx shall remove Power Signal and start digital ping using 360 kHz as operating frequency
after t_nopower. Otherwise, PTx shall remove the power signal and perform digital ping again using 128 kHz and ’Qi_HB_
Low’ digital ping level.

Introduction
In some scenarios, the Power Transmitters cannot compute K-est.
For example:
1.
Digital Ping Level: The PTx cannot accurately estimate the coupling factor because the ping level is out of
range.
2. Timings: The PTx cannot meet the timings for the measurements involved.
3. Confidence: The PTx has low confidence in the estimated coupling factor.
Depending on the scenario, the PTx can correct the operating conditions by itself, or with assistance from the PRx, as
explained in the following sections.

Negotiation Phase - 128 kHz
4.4.1
Nominal negotiation flow
PRx shall use the 128 kHz negotiation phase to select the 360 kHz operating frequency using SRQ/freqsel as described
in Section 4.4.3, Frequency Selection ).
In addition to frequency selection, PRx may perform the following actions before exiting the negotiation phase.
1. Request PTx ID: Retrieve Qi protocol version and manufacturer code using GRQ data packet (Refer to Qi
Communications Protocol for more information)
2. Request Extended PTx ID : Retrieve MPP PTx Extended ID using GET [PTx XID] Request (Section 8.1.16, Get
Request - GET (0x28) )
3. Adjustre-ping duration : Adjust the time delay before the next 360 kHz ping when PRx sends EPT/rep.
It is recommended to perform power related negotiation at the preferred operating frequency i.e. at 360 kHz instead of
128 kHz, to avoid losing the negotiated contract elements due to power signal removal caused by operating frequency
changes.
After completing the transactions, PRx shall terminate the negotiation using SRQ/en and then send EPT/rep to start the
frequency change flow as shown in Figure 17.

4.4.3
Frequency Selection
PRx shall select a new operating frequency (360 kHz) using SRQ/freqsel (Section 8.1.9, Specific Request [Frequency
Selection] - SRQ/freqsel (0x20) ).
After selecting the new frequency and terminating the negotiation using SRQ/en, PRx shall request a re-ping using
EPT/rep to allow PTx to activate the new selected frequency.
1. EPT/rep will cause the PTx to remove the power signal, change the operating frequency to the selected value and
reset the power contract elements.
2. EPT/rst will cause the PTx to remove the power signal, change the operating frequency to 128 kHz and reset the
power contract elements.
PTx shall follow EPT/rep and EPT/rst timings as specified in Qi Communications Protocol book.

4.5
Negotiation Phase - 360 kHz
PRx shall use the 360 kHz negotiation phase to negotiate the required power contract elements before entering power
transfer phase.
PRx shall perform the following actions in 360 kHz negotiation phase:
1. Send ECAP: PRx shall send its extended capabilities data packet to PTx (Section 4.5.1, PRx Extended Capabilities ).
2. Request ECAP: PRx shall request PTx extended capabilities using GET [ECAP] Request (Section 8.1.16, Get Request
- GET (0x28) ).
3. Request PLAP: PRx shall request PTx power loss accounting parameters using GET [PLAP] Request (Section
8.1.16, Get Request - GET (0x28) ) – PLAP exchange is described in Section 4.5.3, Exchange Power Loss Accounting
Parameters .
4. Send PLAP: PRx shall send its power loss accounting parameters to PTx using PLAP data packet (Section 8.1.28,
Power Loss Accounting Parameters - PLAP (0x78) ).
5. Request PLAP2: PRx shall request PTx power loss accounting parameters using GET [PLAP_2] Request (Section
8.1.16, Get Request - GET (0x28) ).
NOTE: The PRx should first check the version in the PTx ID data packet to ensure PLAP2 is supported before sending its
PLA2 parameters.
6. Send PLAP2: PRx shall send its power loss accounting parameters to PTx using PLAP_2 data packet (Section
8.1.32, Power Loss Accounting Parameters 2 - PLAP_2 (0x90) ).
NOTE: If the PTx fails to receive any of the above packets, the PTx should reply NAK to SRQ/en, and remain in the negotiation phase.
The PRx may also perform the following actions before exiting the negotiation phase:
1. Request Extended PTx ID: Retrieve MPP PTx Extended ID using GET [PTx XID] Request (Section 8.1.16, Get
Request - GET (0x28) ).
2. Power Level Negotiation: Refer to Section 4.5.4, Power Negotiation .
3. Exchange Supported Data Streams: Refer to Section 4.5.6, Exchange Enabled Data Streams
4. Send SRQ/pch: Adjust the power control hold-off time,
(refer to the Communications Protocol book).
5. Negotiate other elements described in this chapter
After completing the transactions, PRx shall terminate the negotiation using SRQ/en and transition to Power Transfer
Phase as shown in Figure 20.

4.5.1
PRx Extended Capabilities
PRx shall report its capabilities to PTx using the PRx Extended Capabilities packet (Section 8.1.30, Extended Power
Receiver Capabilities - ECAP (0x84) ).
4.5.2
PTx Extended Capabilities
PRx shall request the PTx Extended Capabilities packet using GET [ECAP] Request (Section 8.1.16, Get Request - GET
(0x28) ). PTx shall respond with PTx FSK ECAP data packet Section 8.2.25, Extended Power Transmitter Extended
Capabilities - ECAP (0x8F:1) ).
4.5.3
Exchange Power Loss Accounting Parameters
PRx shall request the parameters from the PTx using a GET [PLAP] Request (Section 8.1.16, Get Request - GET (0x28) ).
PTx response is described in Section 8.2.21, Power Loss Accounting Parameters - PLAP (0x5F) .
After receiving the parameters from the PTx, PRx shall compute the adjusted coefficients and report the values to the
Power Transmitter using Power Loss Accounting Parameters (Section 8.1.28, Power Loss Accounting Parameters - PLAP
(0x78) ).
4.5.4
Power Negotiation
MPP Power negotiation is performed by the Power Receiver as following:
1. Request PTx Extended Capabilities using a GET [ECAP] Request (Section 8.1.16, Get Request - GET (0x28) ). PTx
response is described in Section 8.2.25, Extended Power Transmitter Extended Capabilities - ECAP (0x8F:1) .
2. Using SRQ/egpl, select a power level ≤Negotiable Load Power value reported in PTx Extended Capabilities
packet.
1. MPP uses Qi EPP terms for describing the potential and negotiable load power.
2. Power negotiation is not required if selected level is equal to default level specified in Table 14
PTx shall report the maximum negotiable power level in the Power Transmitter Extended Capabilities packet based on
the available power in the system.

(0x28) ). PTx response is described inSection 8.2.24, Extended Power Transmitter Identification - XID (0x8F:0) .

4.5.7
Power Control Profile
PRx may request the PTx to change the active power control profile and set limitations on power control methods using
SRQ/pcp (Section 8.1.13, Specific Request [Power Control Profile] - SRQ/pcp (0x20) ).
Power control profile is more likely adjusted during re-negotiation phase.
Refer to Refer to MPP System Specifications - Section 4.9.2.3.4 for more information.
4.5.8
Cloaking Duration
PRx may negotiate the "Cloak Ping Delay" period using SRQ/cloakl,cloakh requests (Section 8.1.11, Specific Request [Cloak
Ping Delay - Low Byte] - SRQ/cloakl (0x20) ) and/or enable Detect Ping using SRQ/detect (Section 8.1.14, Specific Request
[Cloak Detect Ping Delay] - SRQ/detect (0x20) )
Cloaking is described in Section 6.1, Overview .
NOTE: “Cloak Ping Delay” has a length of 2 bytes. The SRQ/en ‘Count’ parameter is only incremented once when modifying EITHER
or BOTH the ‘low’ or ‘high’ bytes—by sending SRQ/cloakl (for the ‘low’ byte) and/or SRQ/cloakh (for the ‘high’ byte).
4.5.9
MPP Proprietary Requests / Packets
The Power Receiver may set custom parameters (power contract elements) in the PTx’s contract using
SRQ/MppProp (Section 8.1.15, Specific Request [Proprietary Parameters] - SRQ/MppProp (0x20) ), or send MPP
proprietary packets.
MPP specifications does not control or regulate the proprietary interactions.
4.6
NFC Identification (Informative)
Power Receivers equipped with NFC readers might be interested in performing NFC identification on the PTx or other
attached accessories. Due to coexistence issues between wireless power signal and NFC, Power Receiver may request a
temporary power signal removal in order to complete the NFC read successfully without any interruptions.
Since the Power Receiver is interested in resuming power transfer after NFC read, it is recommended for the PRx to use
EPT/rep to instruct the PTx to remove the power signal and restart ping phase after a predefined duration of time.
Since the time to finish the NFC scan might vary depending on the NFC technology, number of available tags, etc., the
PRx may negotiate the re-ping time with the PTx during the MPP negotiation phase and renegotiation phase and before
asking the Power Transmitter to terminate the power. PRx may use SRQ/rep to negotiate the power pause period in
MPP negotiation phase. When PRx is ready to start the scan, it may to send the re-ping request.
Power Receiver should choose a value that is long enough to perform the NFC operations without interruptions, and can
also retry again and adjust the timing if the initial requested time was not long enough to perform the NFC operations.

4.7
Changing the protocol version
A PRx may change the version of protocol it implements (e.g. v2.2 after having started in v2.0), by sending SRQ/verSel
during Negotiation to update the Major Version or Minor Version in the power contract. This is an alternative to a PRx
sending EPT/rst, and ID with new values of Major Version or Minor Version (but without the delay associated with
removing the power signal and repeating the 128 kHz and 360 kHz ping sequences).
As with any field in the power contract, the negotiated value is only effective after the PTx accepts the power contract
(i.e. ACK response to SRQ/en). One or more renegotiation phases are typically necessary to negotiate features that were
not supported in the previous protocol version.
When the Major Version or Minor Version is updated in the power contract, a PTx shall implement the requirements
defined in that version of the specification. When a PRx sends SRQ/verSel, the combined value of Major Version and
Minor Version shall be equal to or greater than the combined value in the existing power contract.
SRQ/verSel is supported by PTx that implement protocol version 2.2 or higher.
A PRx shall send SRQ/verSel only in the first 360 kHz Negotiation phase of Full mode that occurs either after the ID &
Configuration phase, or that occurs after Restricted mode to Full Mode Transition without power interruption.
When a PRx sends SRQ/verSel, the Version field of SRQ/verSel shall be set to 0x22 (representing specification version
2.2). A PRx shall only send SRQ/verSel to a PTx reporting v2.2 or higher (PTx version reported in the PTx ID data
packet).
If the PRx chooses to send SRQ/verSel, then it shall implement the following negotiation sequence:
1. Request PTx Version: GRQ/id
2. Send SRQ/verSel
3. Send ECAP (Section 8.1.30, Extended Power Receiver Capabilities - ECAP (0x84) ).
4. Request ECAP (Section 8.1.16, Get Request - GET (0x28) ).
5. Request PLAP (Section 8.1.16, Get Request - GET (0x28) ).
6. Send PLAP (Section 8.1.28, Power Loss Accounting Parameters - PLAP (0x78) ).
7. SRQ/en
NOTE: To enable features specific to v2.2, renegotiation phases are necessary.

Restricted Mode (v2.0) to Full Mode (v2.2).
NOTE: A PRx would typically use CLOAK with FOD reason, to provide the PTx with opportunity to refresh its MatedQ result.

5.
Power Transfer Phase
5.1
Overview
MPP Power Transfer phase is based on Qi EPP specifications i.e., EPP timing specifications, packets, and rules apply to
MPP power transfer phase with minor differences:
1. Frequency dependency : Only 360 kHz operating frequency is supported with MPP Power Transfer Phase, PRx
shall send Qi EPT packets if any other frequency was active.
2. Power packets: MPP extends standard CE and RP packets (XCE - Section 5.2, Extended Control Error Packet , PLA
- Section 5.4, Power Loss Accounting Packet ).
PRx shall issue EPT/rst or EPT/rep when entering MPP power transfer phase if the operating frequency is not 360 kHz.
5.2
Extended Control Error Packet
MPP Extended Control Error Packet is based on standard Qi CE data packet, with an additional communication window
that allows the PTx to communicate with the PRx to either provide feedback (ACK/NAK) or request attention (ATN) for
further PTx-to-PRx communication, as described inSection 8.1.3, Extended Control Error - XCE (0x19) .
(Informative) Allowing the PTx to communicate after every extended control packet improves the latency for some of
the PTx-to-PRx communication flows.

Handling

5.2.2
PTx Response
PTx responses are described in Section 8.1.3, Extended Control Error - XCE (0x19) . Depending on Power Transmitter's
response, PRx may proceed as following:
1. ACK: PTx accepted the requested voltage update. No additional actions required.
2. NAK: PTx rejected the voltage update request. PRx should request the regulation control status packet using GET
request (Section 8.1.16, Get Request - GET (0x28) ) to identify the reason for rejecting the voltage update.
3. ATN: PTx requests to communicate. PRx shall follow the attention handling as described in Qi Communications
Protocol book.
1. PRx may also request the regulation control status packet if PTx responds with ATN
2. PRx may change its behavior depending on the regulation control status result (e.g. if max/min voltage is
reached, PRx may stop to request changes to voltage). The behavior of the PRx is implementation- dependent.
3. A PRx may receive a NAK Response Pattern if the PTx cannot satisfy the XCE request from the PRx. This can
occur if the PTx reached its maximum power capability.
Control status is discussed in Section 5.5, Control Status .

Changing the control method

SRQ/xceMethod and SRQ/xceGain are used to negotiate the following fields in the power contract (that determine the
control method implemented by PTx and PRx):
l Control Method (SRQ/xceMethod) determines which control algorithm is implemented (refer to the MPP
Systembook ):
l Uncompensated (default)
l Gain Linearization
l GSCALE (SRQ/xceGain) contains a gain scaling coefficient. Only applicable when Control Method is Gain
Linearization .
l GTARGET (SRQ/xceGain) contains a gain target coefficient. Only applicable when Control Method is Gain
LInearization.

5.8
Power Modes
5.8.1
Overview
Power modes are power delivery optimizations designed to maximize efficiency and performance within
specific power ranges, certain optimizations may necessitate the precise adjustment of PTx/PRx architecture
to help the achieve the targeted performance.
The system model PTx can adjust its system architecture (e.g. change its series resonant capacitance,
inverter voltage, input supply voltage, etc) to optimize performance for operation within a narrow range of load
power that is a subset of the Guaranteed Power. The basis for the PTx to make these adjustments is a
”Power mode” requested by the PRx.
Allowing PRx to explicitly request optimization for a specific power range eliminates the need for PTx to guess
the optimal power configuration based on PRx’s behaviour. This is especially critical if the system architecture
adjustments are costly i.e. can temporarily disrupt charging performance or may require PTx to first remove
the power signal, which could drastically impact power delivery if the wrong guess is made.
In order to manage different modes efficiently and allow flexible implementations, the communication
protocols allow PRx/PTx to advertise supported modes and explicitly select which mode to use for power
delivery.
The Power Mode indicates a relative range of power levels that the PRx expects to predominantly operate
over. The full operating power range is described by four power modes: Light, Nominal, High, Continuous, as
following:
1. Low power mode (LPM): Operation is deliberately optimized for light load (low power) and low VRECT target.
2. Nominal power mode (NPM): Operation is deliberately optimized for medium power and relatively higher
VRECT target compared to Low power mode.
3. High power mode (HPM): Operation is deliberately optimized for higher power and relatively higher VRECT
target compared to Nominal Power Mode.
4. Continuous power mode (CPM): Operation is uniformly optimized across the full operating range up to the
guaranteed power.
When either the PRx or PTx does not support Power modes i.e. PTx or PRx reports Qi version below 2.2 or devices are
operating in restricted mode, the power delivery mode used is referred to as Default Power Mode.
5.8.2
Definition
Power Modes fall into the following categories:
1. Main Power Mode: Defines the primary operating range of the PRx.
2. Auxiliary Power Mode: Temporary power-related operations nested within a Main Mode. They allow specific
tasks without altering the intended operating range.
Definition of these categories is described in the next sections.

Auxiliary modes enable devices to perform power-related functions without disrupting their intended operating range.

Example of such operation is Gain Measurement. Explicitly requesting the Gain Measurement Auxiliary Power Mode
allows PTx to maintain a known operating condition that is desirable for gain measurement process. For example, PTx
may delay adjusting its resonant capacitance until the gain estimation is complete, as such changes could impact system
gain and lead to inaccurate results.
5.8.2.3
Backwards Compatibility
The Power Mode behaviour in Qi 2.0 and 2.1 is known as the 'Default Power Mode'. PTx shall revert to the Default
Power Mode when communicating with a PRx that does not support Power Mode protocol (i.e. reported protocol
version is 2.1 or lower).
5.8.2.4
Influencing Negotiable Power
Certain adjustments to PTx’s system architecture, as a result of activating specific power modes, may result in a change
to PTx’s power capabilities such as increase or decrease in the maximum power that can be delivered by the PTx. Such
changes are usually reflected on the negotiable power advertised by PTx.
It is not intuitive for PRx to predict how selecting a specific power mode will affect the negotiable power. Therefore, PTx
shall provide this information in advance. PTx shall populate the power capabilities of each of its power modes in the
Power Modes Extended Capabilities data packet (Section 8.2.26, Power Modes Extended Capabilities - MODEXCAP (0xA0) ).

5.8.3
Design Guidelines for Power Modes
PTx implementations may exhibit either Discrete or Continuous operation, and this affects the type of power mode(s)
offered.
5.8.3.1
Continuous operation
This type of PTx exhibits continuous operation regardless of load power. Operation of the PTx across the full range of
load power does not benefit from the PRx reporting power modes (which forecasts future load power).
The PTx does not require the PRx to ensure that an optimal power mode is active. This type of PTx should advertise the
Continuous Power Mode (CPM) to keep the power delivery process simple (and is similar to not operating with power
modes).
PTx architectures with a "buck-boost" or isolated dc-dc converter (i.e. can operate with input voltage above, equal, or
below the output) are capable of operating without interruption across its entire range of load power. A PTx with this
capability should advertise Continuous Power Mode to eliminate unnecessary complexity.
5.8.3.2
Discrete operation
This type of PTx exhibits operation in discrete ranges of load power, and may need to restart to transition between the
discrete ranges. Operation of the PTx across the full range of load power requires the PRx to forecast future load power
(to the PTx), by reporting a power mode that matches its future range of load power. The PTx may require its power
delivery architecture to be adjusted for a change in power mode. Adjusting the power delivery architecture may require
the PTx to remove the power signal.
PTx architectures with a boost or non-isolated dc-dc converter may not be capable of operating without interruption
across its entire range of load power. A PTx with this limitation should use power modes to advertise discrete Power
Modes to co-ordinate these interruptions with the PRx.
A PTx whose input power supply conforms with USB Power Delivery (USB-PD) may require operation in discrete ranges
of load power. Power modes reported by a PRx may be relied upon by a PTx to use the adaptive voltage mechanisms in
USB-PD. Adaptive voltage mechanisms may be associated with a brief removal of the power signal, and power modes
allows a PRx to co-ordinate when this happens.
CPM is mutually exclusive from NPM, LPM and HPM. PTx manufacturers must identify whether their PTx exhibits
Continuous or Discrete operation, and choose the appropriate power mode(s) to advertise (CPM, NPM, LPM, HPM). If
CPM is advertised, no other main mode (i.e. NPM, LPM, HPM) may be advertised, to avoid uncertainty in the power
modes reported by a PRx during power transfer.
5.8.3.3
Backward Compatibility Considerations
PTx manufacturers should design at least one of the power modes to encompass all the functionalities of the default
mode. Such that, a PTx starting in default mode for backward compatibility reason may seamlessly transition from
default mode to one of the main power modes supported by the specifications after identifying the PRx.
For instance, a PTx capable of supporting CPM may initially operate in default mode but, upon recognizing the PRx's
capabilities, can switch to CPM as the active power mode. Similarly, power transmitters using discrete operation modes
may select Nominal Power Mode after identifying the PRx, provided that Nominal Power Mode encompasses all
functionalities of default mode.

5.8.5
Power Mode Selection
A power mode request is a best effort estimate of future load power levels. Regardless of power mode, a PRx may
operate at any level up to the guaranteed power.
The power mode requested by a PRx provides a PTx with information to optimize future performance, by preemptively
adjusting the PTx system architecture. Each adjustment to system architecture is subject to hysteresis and changeover
delays or glitches, which negatively impact system performance. The power mode request helps a PTx to minimize how
frequently it adjusts its system architecture, thus minimizing the negative impact of each adjustment.
PRx may initiate a mode change request using Mode Select Request (Section 8.1.1, Mode Select Request - MSR - (0x13) )
data packet during Negotiation Phase or Power Transfer Phase. PTx shall respond with status report using Mode Select
Status (Section 8.2.8, Mode Select Status - MSS - (0x23) ) data packet until the change in system architecture is either
completed or rejected.
There are four potential status responses to a Mode Select Request data packet; SUCCESS, FAIL, BUSY, or PENDING (see
Figure 38).

following values: SUCCESS, FAIL, or BUSY. If the reported status is PENDING, the transaction is still in progress; in this
case the PTx shall complete the transaction within

1. Previous Mode == New Mode: PTx should continue processing the previous request and report
accurate status in MSS data packet (i.e. PENDING, SUCCESS, FAIL)
2. Previous Mode != New Mode: PTx may respond with BUSY status to reject the transaction, or may abort the
pending transaction and start processing the new one.

5.8.5.3
Specifying Preference for Power Transfer Contract Retention
PRx is aware that PTx may sometimes be unable to perform power mode changes while retaining power transfer
contract context (i.e. PTx is unable to avoid power interruption or unable to use cloak to execute the power mode
changes). Given this limitation, PRx may choose to avoid power mode changes altogether to prevent the loss of power
transfer contract context.
Determining power transfer contract retention possibility in advance may be challenging for PTx, as it largely depends
on the active power mode and the targeted power mode requested by PRx. The wide range of possible combinations
makes it difficult to perform a definitive evaluation prior to receiving the mode select request; therefore, the assessment
can generally only be made once the request is received. It is recommended that PRx specify its power transfer contract
retention preference in the power mode select request. PTx should honor this preference either by preventing power
interruption completely, if feasible, or by using cloak to retain the power transfer contract. If PTx is unable to meet the
preference, it shall return a FAIL status with the error code SESSION_PREF_NS. PRx can then choose to reconsider its
decision and forgo the power mode change operation.
In other cases, PRx may ask the PTx to not preserve the power transfer contract and instead perform a communication
restart when applying the new power mode. PTx shall request a power interruption using EPTR data as packet as
described in Section 5.8.5.2, Temporarily Interrupting Power Delivery to Perform Power Mode Changes after reporting
PENDING in MSS.
Alternatively, PRx may choose to not specify a preference. In this case, PTx is free to use any appropriate method to
execute the power mode selection request. Preference options are described in Table 24.

5.8.5.4
Requesting Power Mode Changes in Negotiation Phase
PRx should identify the PTx’s power mode capabilities and select the future desired power mode for power delivery
during Negotiation Phase (128 kHz and 360 kHz), prior to entering the Power Transfer Phase. Early selection allows the
PTx to prepare accordingly, potentially reducing the overall time to reach the target power.
5.8.5.4.1
128 kHz Negotiation Phase
Power mode selection during 128 kHz negotiation phase provides a hint to the PTx regarding the power mode that is
going to be used during 360 kHz power transfer phase. PTx should utilize the re-ping window between 128 kHz and 360
kHz ping phase to apply power modes changes and avoid additional interruptions if possible. For the PTx to leverage the
frequency transition window to perform power mode changes, the duration of the window should be negotiated by PRx
to a value equal to
or larger using SRQ/rep.
Figure 44 - Power Mode Selection During 128 kHz Negotiation Phase
5.8.5.4.2
360 kHz Negotiation Phase
PRx shall identify PTx’s power modes capabilities and select the appropriate power mode for operation before entering
360 kHz Power Transfer Phase. This ensures that the desired power optimizations are enabled for starting power
delivery.
NOTE: If using SRQ/verSel, power mode selection is performed in a renegotiation phase.
NOTE: This also applies in the 360 kHz negotiation phase following a restricted mode to full mode transition.

5.8.8
Handling Communication Failures
This section describes the recommended PTx’s behaviour when communication failures occur.
5.8.8.1
Communication Timeout
Noise and rapid changes in system load may corrupt communication during power delivery and may result in loss of
communication and possibly removal of power signal due to communication timeouts. This event is referred to as
Communication Disconnect.
PTx should retain the power mode that was selected before the communication disconnect and continue using it when
re-establishing the connection, this allows both PTx and PRx to resume power transfer quickly.
Figure 48 - Example: Retaining Power Mode After Communication Disconnect
5.8.8.2
Digital ping failure after power mode change
It is possible that the activation of a specific power mode may change the operating point of the digital ping performed
by PTx. Depending on the state of PRx or the coupling conditions, the new operating point chosen by PTx may not be
reliable to establish communication, leading to digital ping failures. PTx shall revert the power mode changes and select
a reliable power mode after failing two digital ping attempts.
Figure 49 - Power Mode Revert After Digital Ping Failure
PRx can utilize the reference voltage reported by PTx in the Power Modes Extended Capabilities data packet (Section
8.2.26, Power Modes Extended Capabilities - MODEXCAP (0xA0) ) to assess whether the digital ping operating point meets
its requirements before selecting the appropriate power mode.

5.9
Delta Ploss Calibration
5.9.1
Overview
Delta Ploss calibration monitors the change in power loss estimates during power transfer, which can be used for
detecting whether a foreign object has been inserted within the active area of the interface surface during power
transfer. Calibration should be performed accounting for the following conditions:
1. Mated-Q Test (performed using Open-Air Q-Test data) indicates FO is not present on charging surface
2. Time between last performed Open-Air Q-Test and the PLOSS calibration start should be short [ t_ref ]
3. Total calibration time shall not exceed [ t_cal ]
4. FO safety checks are performed live while calibration is on-going
Figure 63 - Delta Ploss calibration conditions
5.9.2
Choosing not to begin Calibration (PRx)
A PRx may choose not to begin Calibration if:
l it is not ready
l it cannot operate at the load power level it requires for calibration (e.g. conditions prevent operating above 15
W)
5.9.3
Performing Mated-Q FOD before starting Calibration (PTx)
When a PRx sends CAL_ENTER (to start Calibration), after tref has elapsed, a PTx requests to perform Mated-Q FOD by
responding with CAL_ENTER_RSP containing:
l Response = REJECT
l Reason = FOD_REFRESH_REQ
A typical scenario when the PTx may do this is when excessive time has elapsed since last performing Mated-Q FOD.
When a PTx sends CAL_ENTER_RSP with Reason = FOD_REFRESH_REQ, a PRx should allow a PTx to perform Mated-
Q FOD by sending CLOAK containing:
l Reason = Cloak: Foreign Object Detection
A CLOAK packet containing Reason = "Cloak: Foreign Object Detection" enables a PRx to quickly resume power delivery
(i.e. without restarting from Ping) after providing an opportunity for a PTx to perform Mated-Q FOD.

6.
Cloak Phase
6.1
Overview
Cloak is a method for momentarily interrupting power transfer without notifying the user and without resetting the
negotiated power transfer contract elements. Power transfer may be interrupted for several reasons including thermal
management, power budget changes, coexistence, and many others.
1. Unlike Qi EPT data packets, cloak request allows PTx and PRx to maintain the negotiated power transfer contract
elements upon cloak entry/exit.
2. Cloak requires the Power Receiver to have a power storage element (e.g. battery) in order to retain state and
other information after the removal of the power signal.
Cloak State can be initiated by PRx or requested by PTx using MPP CLOAK data packets (ASK:Section 8.1.2, Cloak - CLOAK
(0x18) , FSK: Section 8.2.5, Cloak Request - CLOAK (0x1E:0) ).
Cloak State begins once PTx terminates power transfer following the processing of ASK CLOAK data packet. Cloak State
is a period of power interruption, followed by a brief period of power transfer. The short period of power transfer is
known as cloak ping. The Power Receiver may choose to remain in Cloak State by responding to a cloak ping with a
CLOAK data packet or may choose to exit cloak state by initiating cloak exit handshake as shown in Figure 71.
Cloak exit handshake is described in Section 6.4, Cloak Exit .
6.2
Cloak Ping Requirements
1. PRx shall disconnect its load, and honour the 1 MHz resonance requirement within the time window

detecting the removal of the power signal (power interruption period). Refer to the Communications Protocol
book for more information on

2. PTx shall proceed to ping phase (disconnect) if free air response (object removal) is detected.
6.3
Cloak Entry
PTx and PRx are allowed to initiate cloak entry at any time in Power Transfer Phase. The procedure is described in the
following sections.
While in Cloak Phase, PTx shall abandon the Cloak Phase and proceed to Ping Phase if one of the following error

1. PTx receives a packet other than CLOAK or cloak exit sequence packets
2. Cloak Timeout Timer tcloaktimeout expires Table 29)
PRx shall abandon the Cloak Phase and proceed to ping phase if a cloak ping did not arrive within tcloakpingtnext duration.

6.4
Cloak Exit
The PRx may decide to exit cloak phase when ready to resume charging by initiating the cloak exit sequence upon
detecting the next cloak ping by sending the following packets:
1. REPORT [PRx ID] - Report PRx ID to PTx Section 8.1.26, Report [PRx Identification] (0x58:0) )
2. GET [PTx XID] - Request PTx XID (Section 8.1.16, Get Request - GET (0x28) )
Both PTx and PRx shall exit Cloak Phase and transition to Power Transfer Phase after processing the FSK response of
GET [PTx XID]. PTx and PRx shall transition to Ping Phase if unexpected identifiers or unexpected (illegal) packets were
received.
Exchange of identifiers allows the PRx and PTx to detect device swap during cloak.
The PTx may need to communicate with the PRx in some circumstances during cloak (i.e., change in adapter available
power). The PTx may request to exit cloak state by responding to CLOAK data packet with FSK ATN pattern. The PRx
will either service the PTx communication request and start the cloak exit sequence by responding with the PRx ID
report packet, or deny it by responding with a CLOAK[forced] cloak data packet. If the PRx decided to honour the cloak
exit request, the PRx shall send DSR/POLL to the PTx after entering power transfer phase to allow the PTx to send any
pending messages.
In the case of PTx initiated cloak, the PTx may exit cloak phase earlier than
, according to the PTx operation status.
PTx shall remove power and move to the ping phase (abandoning the cloak) if three consecutive cloak exit requests
packets were denied or timed out. Otherwise, the PTx shall acknowledge receiving CLOAK[forced] data packet and
remain in Cloak Phase
Power transfer phase timeouts are reset after exiting cloak and shall restart counting upon entering power transfer
phase.
EXAMPLE:
XCE, PLA, Data Streams, etc. timeouts are reset upon cloak exiting. The reference time for Power Transfer
Phase after exiting cloak is the end of the PTx ID packet.
If PRx denies a cloak exit attempt by PTx then PTx should delay messages until power transfer phase.

7.
Extended Data Streams
7.1
Overview
MPP extends Qi EPP data stream definition for application-layer data exchange to add support for:
1. Concurrent Streams : Allow data transfer across multiple (different) streams concurrently.
2. Extended Status Codes : Report different status codes to enable different retry behaviors.
3. Data Integrity : Handle data errors in the stream layer and detect errors using CRC-16.
4. Exchange SupportedStreams : Allow devices to exchange supported streams on both sides.
MPP supported data streams and their unique identifiers are described in the Table 30.
Table 30 - Data Streams Identifiers

Devices should exchange supported streams by sending Enabled Streams packet (Section 8.1.17, Enabled Data Streams -
EDS (0x29) ) in MPP negotiation phase (Section 4.5.6, Exchange Enabled Data Streams ).
For generic application data transfer, MPP PRx and MPP PTx shall only use MPP Extended Data Streams (the data
streams defined in Qi EPP are not supported).
NOTE: It is recommended that if a PRx requests to open a data stream using an Identifier number not supported by the PTx, the PTx
should deny the request and refuse to open a data stream.
7.2
Simultaneous Data Stream Extension
Concurrent streams support different applications to share the stream bandwidth e.g. if a long stream message is being
transferred, a short message from a different stream can be sent concurrently with the long one without having to wait
for the long transaction to finish.
Support for concurrent streams is added by introducing a stream header to standard Qi EPP Data Stream packets
(Auxiliary Data Control, Data Stream Response, Auxiliary Data Transport) resulting in new packets definition for ADC
and DSR. ADT Packets are re-defined such that the first byte of the payload is always assigned to the stream header.
ADT packets with 1-byte payload (i.e., 0x16, 0x17) shall not be used with Simultaneous Data Stream Extension. The size
limitation does not allow the packet to carry the stream header and the payload in a single transfer.

The simultaneous version of the data stream packets is defined as:
1. Simultaneous Auxiliary Data Control (S-ADC): ASK/FSK packets to Reset, Open, and Close a specific data
stream (Section 8.1.23, Simultaneous Auxiliary Data Control - SADC (0x48) , Section 8.2.18, Simultaneous Auxiliary
Data Control - SADC (0x4F) )
2. Simultaneous Data Stream Response (S-DSR): ASK/FSK packets to report extended status code (e.g. ACK, ERR_
BUSY, ERR_UNEXPECTED, etc.), used as a response by both PRx and PTx to S-ADC (ASK/FSK) packets (Section
8.1.22, Simultaneous Data Stream Response - SDSR (0x38) , Section 8.2.14, Simultaneous Data Stream Response -
SDSR (0x3F:1) ) and FSK ADT packets.
3. Simultaneous Auxiliary Data Transport (S-ADT): ASK/FSK packets to transfer data payload with stream
header.
PTx shall use FSK patterns when responding to ASK S-ADT packets.    
Section 7.4, Examples shows examples on how to use and handle data streams.
7.2.1
Error Handling
During a data stream transfer, communication errors might affect the ability to correctly decode ASK/FSK packets,
leading to a synchronization issue when handling data streams.
MPP PRx and PTx shall follow the data stream error handling as described in Qi EPP specifications. When retrying ASK
packets, it is important for PRx to handle the following cases:
1. Retrying S-DSR: S-DSR Packet shall be retried with standard DSR/POLL to avoid accidentally acknowledging
ADT/ADC packets.
2. Retrying S-ADC / S-ADT: Packet receiver shall re-acknowledge repeated S-ADC[open/close], ADT requests if
applicable.

7.2.3
Cloaking Compatibility
If cloaking is initiated during data stream transfer, all active transfers shall be terminated and flagged as incomplete
transactions and may be restarted after exiting cloak.
NOTE: The requirement to terminate active data stream transfers applies to cloaking only. The data transfer stream should not be
interrupted during instances of renegotiation or power throttling.
If the device decides to restart the interrupted transaction, then it shall start the transaction from the beginning by
opening the stream using SADC, transferring the payload from scratch using SADT packets, closing the stream using
SADC.
An example is provided in Figure 94.
7.3
Data Integrity Extension
The data stream initiator shall compute and report a CRC value in the S-ADC[Close] request at the end of the data
stream transmission. If the data stream recipient detects an error in the data transmission when comparing the
computed CRC value against the received one, it shall drop the received data stream payload and report the error to the
sender using S-DSR with ERR_CRC code. The data stream initiator should repeat (resend) the payload.
MPP uses CRC-16-CCITT to ensure the integrity of the payload transfer over the inductive link. The polynomial is
described as following:

8.1.35
Proprietary - PROP (multiple headers; multiple types)
The MPP Specification does not define the formats of proprietary data packets.
It is optional for a Power Receiver to send proprietary data packets. The WPC does not manage the use of these data
packets. Accordingly, the Power Receiver should verify the type and make of the Power Transmitter before using
proprietary data packets.
l In the configuration phase, a Power Transmitter shall treat all proprietary data packets as status update data
packets.
l In the negotiation phase and renegotiation phases, the Power Transmitter shall treat all unsupported proprietary
data packets as simple-query data packets, responding with ND.
l In the power transfer phase, a Power Transmitter shall treat all unsupported proprietary data packets as status-
update data packets.

A.1
Protocol Carrying Delta Ploss Calibration Across Power Modes
In Figure 155, Delta Ploss calibration is completed in nominal power mode before the PRx requests to enter high power
mode. The PTx retains the previously calibrated parameters across the power mode transition. This method avoids a
phase-shift whilst allowing the system to take advantage of high power mode optimisations.
Figure 155 - Retaining Delta Ploss calibration during power mode transition from NPM to HPM
A PRx may request to enter HPM via cloaking (i.e. MSR preference as “preserve the power transfer contract”) after
calibration. The PTx saves the calibrated parameters (α, β) across power mode transitions via cloaking.
The steps below describe the stages outlined in Figure 155:
1. The PRx starts up in nominal mode and completes Delta Ploss calibration.
2. The PRx requests the calibration parameters (α, β) from the PTx using the GET data packet, then stores the
parameters.
3. The PRx requests to enter high power mode using the MSR data packet, indicating a preference to perform a
power mode transition via cloaking.
4. For a PTx that requires power removal for power mode transitions, the PTx reports "PENDING" in its MSS data
packet, and requests to enter the cloak phase.
5. After the PTx completes the power mode transition, the PTx requests to exit the cloak phase.
6. The PRx confirms that the power mode transition was successful via the DSR/poll data packet and the PTx
reports "SUCCESS" in its MSS data packet.
7. The PRx confirms its current power capability, and a PTx that has retained the Delta PLoss parameters into high
power mode advertises 25 W negotiable power. If a PTx cannot support 25 W, it notifies the PRx.
8. The PRx requests the calibration parameters again using the GET data packet. The PTx responds with the dPCAL_
PARAM data packet. The PRx then checks whether the calibration parameters in high power mode match those
stored while in nominal power mode. These parameters should match if the PTx continues to advertise 25 W
support.
9. The system proceeds in high power mode during the power transfer phase.

A.2
PRx-Initiated Re-Calibration Sequence
In a scenario where the PRx detects that the rectified voltage levels deviate significantly from those used to generate the
Delta Ploss linear fit, the PRx can request recalibration using EPT/rcl.
Figure 156 - PRx initiates Delta Ploss recalibration
.
The PRx uses EPT/rcl to trigger the PTx to clear the stored parameters, re-perform the Mated-Q Deflection test, and
transition between power modes (e.g. from high-power mode to nominal power mode) when necessary; during these
steps, the PTx can mask its UI (i.e. either audible/visible or both) to provide a better user experience.
The steps below describe the stages outlined in Figure 156:
1. The PRx decides to recalibrate by sending an EPT/rcl data packet.
2. The PTx removes the power signal, clears the stored Delta Ploss parameters, and resets. The PRx masks its
charging UI throughout the restart sequence.
3. The PTx restarts in a power mode requested by the PRx. This could be different to the power mode in which the
previous calibration took place (e.g. the PRx triggers recalibration from within high power mode, and requests to
restart in nominal power mode for calibration).
4. The system performs Delta Ploss recalibration.
